# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Single-user personal health tracker. The owner sends natural-language Telegram messages ("40g jumbo oats", "12000 steps", "weight 72.6", "1 latte"); Claude routes+extracts them into tool calls; deterministic executors write the data. The bot runs locally on the owner's Mac as a launchd agent that long-polls Telegram.

## Commands

```bash
# One-time setup
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
cp .env.example .env                       # fill in what the entrypoint needs (the file says which)

# Try it with no API key: seed a week of demo data, then read it back
.venv/bin/python -m health.seed_demo --days 7 [--reset] [--today YYYY-MM-DD]
printf '/today\n' | .venv/bin/python -m health.cli
.venv/bin/python -m health.cli             # interactive; free text needs ANTHROPIC_API_KEY
                                           # HEALTH_TODAY=YYYY-MM-DD pins the date both resolve to

# Run the bot in the foreground (needs .env; see Config)
.venv/bin/python -m health.main

# Manage the resident launchd agent (the "live" bot)
./scripts/bot.sh install     # render the plist for this checkout, (re)load, start — use this after a clean stop
./scripts/bot.sh restart     # kickstart -k; only works if already loaded
./scripts/bot.sh status      # state / pid / last exit
./scripts/bot.sh logs        # tail data/logs/bot.err.log

# Rebuild the SQLite projection from the JSONL system of record
.venv/bin/python -m health.rebuild_db [--skip-bad-tail]

# Load the example catalog (health/example_catalog.py; idempotent, dedupes on slug)
.venv/bin/python -m health.seed_catalog

# What the bot is costing, totalled out of the transcript (hit% + calls/message)
.venv/bin/python -m health.report_usage [--days 7]

# Tests and lint
.venv/bin/python -m pytest
.venv/bin/ruff check .
```

- **After editing code, the live bot needs `./scripts/bot.sh restart`** — launchd runs a resident copy; edits don't take effect until restart.
- **Tests** live in `tests/` (pytest; `pip install -e ".[dev]"` brings it and ruff). Run `.venv/bin/python -m pytest`. They cover the core invariants — food scaling/`each`-vs-mass units, the estimate gating, runtime provenance + JSONL-before-projection write order, and the `rebuild_db` round-trip (which now includes corrections *and* `set_meal`: deleting either `ingested_at` guard fails several tests, including snapshot equality) — plus the pure `targets.py` math. **The suite is hermetic and MUST stay that way:** `tests/conftest.py` redirects `DATA_DIR`/`DB_PATH` to a tempdir *before the first `health` import* so tests never touch the owner's real `data/`; `tests/test_isolation_guardrail.py` fails loudly if that ever breaks. `ruff check .` is the linter — correctness rules only, configured in `pyproject.toml`; CI (`.github/workflows/tests.yml`) runs it plus the suite on 3.11–3.13 plus a keyless `seed_demo` → `/today` → `rebuild_db` → `/today` round-trip that must diff empty. For runtime behaviour a test can't reach (Telegram wiring), still verify by driving the flow and inspecting `data/*.jsonl` + the projection. The harness tool-use loop is covered via the `fake_client` fixture in `conftest.py` (a scripted Anthropic stand-in; `calls[i]["messages"]` is what makes context assembly assertable) — see `tests/test_harness_history.py`.
- Logs: `data/logs/bot.err.log` holds stderr *and* all app logging (`bot.out.log` is usually empty). Note: the httpx logger is silenced to WARNING because getUpdates URLs embed the bot token. **For "what actually happened in that conversation?" read `data/messages/<date>.jsonl` instead** — `bot.err.log` deliberately carries no message text.

## Architecture — the chassis

Every message follows one feature-agnostic path (`docs/architecture.md` is the original spec, with notes on what moved):

```
Telegram update → adapter → NormalizedMessage → harness.handle → Claude tool-use loop → executor → writer.record → JSONL (+ SQLite projection) → reply
```

- **Adapter** (`health/adapters/telegram_adapter.py`) — the only channel-specific code. Translates updates to/from `NormalizedMessage`, enforces the allowlist, runs the blocking `harness.handle` in a worker thread, and always replies (on failure it sends a "nothing was logged" message — a handler exception never leaves the user hanging). The deterministic slash commands (`/today`, `/yesterday`, `/week`, `/last N`, `/catalog`) live in `health/adapters/entries_view.py`, channel-neutral, so `health/cli.py` renders them from a terminal with no model call and no key; free text in the CLI goes through the same `harness.handle` on one reply handle per session, which is what keeps propose → "yes" working there. `health/seed_demo.py` writes a week of demo data through the executors (never around them).
- **Harness** (`health/core/harness.py`) — the only "smart" part. Builds a thin system prompt, calls the Anthropic API with *all* registered tools, and loops running executors until Claude returns plain text. Claude does **routing + extraction only**. The loop is bounded at `MAX_LOOP_ITERATIONS` (12) and returns an honest "hit my internal tool-call limit" reply on exhaustion. That reply says work **may already have landed** and to check `/today`: it used to say "nothing further was executed", which reads as "nothing was executed", and the obvious response — re-sending — double-counts everything the twelve iterations did commit. It also declares `SERVER_TOOLS` — `web_search` (localised to GB) and `web_fetch` — which run on Anthropic's side and have no executor; that's chassis infrastructure like `MODEL`, not a feature, so invariant 5 holds. Server tools make `stop_reason: "pause_turn"` reachable: the loop re-sends the paused turn unchanged to resume it, because read as a final response it would ship a truncated reply. **Client `tool_use` blocks are collected BEFORE that branch** — a turn can carry one alongside a paused server tool (the 2026-07-26 `container_id` incident is exactly that pairing), and the pause used to `continue` past the dispatch entirely, so the food it would have logged was never written and an unanswered `tool_use` went back to the API. The pause only short-circuits when there is nothing local to run. **They also make the turn stateful: `web_search_20260209` filters its results in a server-side code-execution container, so once a response carries `container.id` every later request in that turn must pass it back as `container=`** — without it the API 400s with "container_id is required when there are pending tool uses generated by code execution with tools", which is what broke a search-plus-`propose_food_estimate` turn on 2026-07-26 (user saw "nothing was logged" *after* the executor had committed). The id is a local, so it resets per message; both continuation paths need it, which is why it's threaded at the top of the loop rather than in either branch. It also writes the conversation transcript (`health/store/msg_log.py`): inbound message, every tool call with its result or error, every server-tool call and outcome (`_record_server_tools`, kind `server_tool` — a separate kind because nothing here dispatched them), and the final reply.
- **Executors** own the *work* — deterministic, dumb. They build SI-unit fields and call `writer.record()`; they never touch raw text, time, source, or SQL directly.

**Core invariants (breaking one means the feature is wrong, not the rule):**
1. **Claude dispatches; it never computes.** All arithmetic lives in executors (see the "never do arithmetic" rule in `health/core/prompts.py` and the sizing math in `targets.py`).
2. **JSONL is the system of record; SQLite is a disposable projection.** `writer.record()` appends the canonical JSONL line *first*, then upserts the projection, then appends provenance to `ingest_log.jsonl`. (`data/messages/` is *not* a system of record — see the transcript note below.)
3. **`project()` is one idempotent upsert used by BOTH live ingest and `rebuild_db`** — that's what guarantees a rebuild reproduces live-ingest state. It's an `ON CONFLICT(dedupe_key) DO UPDATE`. **The one sanctioned exception is `corrections`**, which owns no table and instead applies an `UPDATE`/`DELETE`/`relabel` to the *target* feature's table — still idempotent, and still the same function for both callers.
4. **Provenance is runtime-authored, never model-authored.** `raw`/`source`/`ingested_at`/`schema_version` are stamped by `writer.record()` from the `current_message` contextvar (`health/core/contracts.py`), set for the duration of each turn.
5. **The core never references a specific feature** — it only knows the registry.

**The system prompt is sent as two blocks, and the split is load-bearing for cost.** Block 1 is `prompts.STATIC_PROMPT` — byte-identical on every request — and carries the single `cache_control` breakpoint; because the rendered order is tools → system → messages, that one breakpoint covers the tool schemas *and* the prompt body, ~7,700 tokens that were otherwise re-sent in full on every one of the ~2.1 API calls a message costs. Block 2 holds everything per-turn: the clock and the `system_context` fragments. The clock **used to head the prompt**, and that alone made the whole prefix uncacheable — caching is a prefix match on exact bytes, so a value that changes every minute at the front invalidates everything after it. `STATIC_PROMPT` is a module constant, not something a function assembles, so "byte-identical" is structural rather than a discipline. **Prompt caching fails silently** — a stray per-request value in block 1 produces no error, just a fresh write on every call — so the only detector is `report_usage`'s hit% column, and `tests/test_prompt_cache.py` pins the breakpoint's exact position. Do **not** replace it with the top-level `cache_control=` parameter: that auto-places on the *last* cacheable block, i.e. the volatile one, which still reports non-zero `cache_creation_input_tokens` and so looks like it works.

The system prompt is deliberately thin (just today's date/time + routing rules). Conversation history is **bounded and ephemeral** (`health/core/history.py`): the last 10 turns per chat, dropped after 90 minutes idle, in-process only (lost on restart), and **plain text only** — never the `tool_use`/`tool_result` blocks, which would risk an orphaned `tool_use` and re-feed stale tool results. It feeds the model's context and nothing else; provenance is still stamped from the live message, never from history. A feature that needs *structured* cross-turn state still surfaces it via a `system_context` fragment (e.g. food's pending-estimate awaiting "yes") — history is the conversational fallback, not a substitute.

**The bot is biased to act, and may ask at most one question** (`prompts.py`, and the SAVED FOODS fragment in `food.py`). Default behaviour is unchanged: estimate, log, and say what you assumed; the user corrects. **Whether a question earns its round-trip is the model's judgement** — the prompt gives cases where it usually does (a destructive instruction with several plausible targets, a self-contradicting message, an unboundable amount) as examples, not as a closed list, because on Opus 5 an enumeration gets followed literally. Two rules are not negotiable: the question must restate the item so the answer stands alone, and it must never re-ask a detail the same reply already settled with a stated assumption. A follow-up question should add information the estimate did not already state. The save offer may now ask or not, as the food warrants.

This used to be a flat "never ask", after the catalog prompt caused repeated clarification. It was relaxed deliberately, and the three things that made that failure possible are gone: there was **no conversation history at all** then, so the answers landed on turns that couldn't remember asking (history exists now, and `IDLE_EXPIRY` is 90 minutes); nothing capped the number of questions (one per reply now, asserted in `tests/test_prompts.py`); and acting wrongly was unfixable, which made asking feel safer than guessing (corrections make a wrong guess a one-message fix). If you find yourself re-tightening this, check those three still hold rather than just reverting the wording.

## Adding or changing a feature

A feature is one module under `health/features/` that declares a `Feature(...)` — `tools` (Anthropic schemas), `executors` (name→fn), `schema` (DDL, uses `IF NOT EXISTS`), `domain` (its `data/<domain>.jsonl` + table), `dedupe_key`, `project` (the upsert), an optional `system_context`, and an optional `verbatim_blocks` (result keys holding finished text the reply must reproduce exactly — the harness restores them). **`health/features/steps.py` is the reference template**; copy its shape. The **only** shared-code edit is adding the feature to `FEATURES` in `health/core/registry.py`. Everything else lives in the module.

A **read-only** feature just omits `schema`/`domain`/`project` — the defaults allow it and `ingesting_features()` filters it out, so it adds a tool without adding a system of record. `review.py` is the template for that shape.

Active features: `steps`, `weight`, `food` (two features — catalog + log), `measurements`, `exercise`, `review` (read-only), `corrections`. No stubs remain; the meals layer is queued in `docs/roadmap.md`. `targets.py` is a **compute lib, not a routed feature** (no tools) — imported by `food` and `review`.

**`corrections` MUST STAY LAST in `FEATURES`.** `rebuild_db` replays domains in list order, and a correction has to land after the rows it corrects. Registry order is load-bearing here, not cosmetic — `tests/test_registry.py` asserts it.

## Data model specifics (the non-obvious parts)

- **Food is two features in one module** (`health/features/food.py`): `food_catalog` (reusable foods, macros stored per a reference portion `ref_qty`/`ref_unit` ∈ `g|ml|each`, dedupe on `slug`) and `food_log` (one row per eating event). Logging scales catalog macros by `amount / ref_qty`.
- **Meat and fish state their basis.** Catalog entries specify raw or cooked weight. To convert a raw label to a cooked basis, divide per-weight values by the cooking yield and document the source panel and yield in the notes.
- **`each`-unit catalog foods scale by count, not weight.** A food stored as `ref_unit="each"` (e.g. a banana, an egg) counts whole units — a stated gram weight is ignored. Foods you weigh per portion (e.g. salmon) should be stored per `100 g` so `"2 fillets 90g each"` scales to 180 g. Gram-weights hidden in `notes` are human-readable only; the executor doesn't parse them for scaling (except `targets._typical_serving`, which reads a "typical serving Ng" note for suggestion sizing).
- **User-given macros can be stated per a different reference amount.** A message like "per 100g: 184 kcal … I ate 63g" is logged via `log_food` with the macros verbatim plus `macros_ref_qty: 100`; the executor scales by `quantity / macros_ref_qty` (and `save: true` stores the *stated reference* as the catalog portion, not the eaten amount). Before this field existed (2026-07-25), that message shape logged per-100g macros unscaled against 63g.
- **Macros are all-or-nothing, and their basis is not guessed at** (`_given_macros`, `_macros_reference`, 2026-09-01). Three silent traps, all closed in the executor because the tool schema is a request and not an enforcement:
  - `has_macros` demanded all five while the schema only required `name/quantity/unit`, so an item giving **four of five** (fibre is the one that gets forgotten) fell through to the catalog branch and logged **stale catalog macros**, discarding the label the user had just read out — no error, nothing in `unresolved`. Partial input now raises.
  - A reference amount is required for quantities other than one. Defaulting to the eaten amount would treat per-item macros as a total.
  - A per-100g reference on an `each` item divides every serving by 100, and with `save: true` freezes "per 100 each" into the catalog so every FUTURE log divides by 100 too. Rejected above `_MAX_EACH_REFERENCE` (12).
- **Calories are cross-checked against their own macros.** Mixing per-portion calories with per-100 g macros can yield an inconsistent row. The tool warns when both the fractional and absolute thresholds are exceeded.
- **`_norm_unit` rejects a unit outside `g|ml|each`.** It used to pass anything through lowercased, so `tbsp` stayed `tbsp`: it matches no catalog entry, and on the save path freezes a reference portion nothing can ever scale. `save_food` likewise refuses `ref_qty <= 0` — every log of that food divides by it, and a zero makes the whole evening raise *after* rows have committed (the suggestion pass divides by it too), so the model reads "nothing was logged" and retries into duplicates.
- **Food rows dedupe by ingestion time** so a genuine second helping adds a row. A confirmation may repeat the earlier food. The executor checks the same date, meal, slug, amount, and unit within its duplicate window. An explicit override permits an intentional repeat.
- **Estimated foods are gated, and the gate's rule is "the user has seen it".** Catalog hits, user-given macros and zero-calorie items (step 1 of the ladder above) auto-commit; a food Claude must *estimate* goes `propose_food_estimate` → shown to user → `confirm_pending` on their "yes". Note a directly-logged zero carries `estimated: 0`, since that flag means "came through propose/confirm" and nothing else. Pending state is in-process only (`_pending`), lost on restart.
  - Same-turn confirmation requires the previous assistant reply to have shown the estimate. The check compares each row's rounded calories with the previous reply.
  - **A refused confirm raises**, it doesn't return `{"error": ...}`. Returned as data the model read it as advisory and answered it with a confident "Logged" plus an invented progress block. `writer.record` is never reached, so the pending survives the raise.
  - An explicit meal supplied at confirmation replaces the staged label.
  - **Confirmation names the intended food.** A chat's pending slot can still hold an earlier item. Matching accepts the exact slug or a shared distinctive word.
  - **`propose_food_estimate` MERGES within one turn** rather than assigning. Two proposals in one turn is a legitimate shape (a mixed dish split, or a second food after logging a first), and overwriting destroyed the first while the reply named both, so the user's "yes" committed only the survivor. Across turns the newer proposal still replaces the older one.
  - A pending goes stale after `PENDING_EXPIRY` (= `history.IDLE_EXPIRY`) and `_pending_section` stops advertising it. Before that it had no bound at all.
- **Daily targets** live in `health/config.py` (`DEFAULT_TARGETS`, overridable per key with `TARGET_*` in `.env`); `targets.py` imports the result and owns only the semantics (kcal and fat are ceilings, protein/fibre floors, carbs tracked). Change `.env` + restart; the test suite pins the defaults in `conftest.py` so a developer's override can't move the block assertions. Evening catalog suggestions kick in past `SUGGEST_AFTER_HOUR` (16:00 local); `suggest_food` answers the same question on demand at any hour.
- **The harness repairs rendered blocks.** Features declare which result fields carry finished text. An ASCII skeleton matches returned lines even when icons are swapped or omitted. Repair happens before saving history and transcript.
- **A rendered line without a tool result is stripped.** The feature signature identifies lines it owns. The harness drops lines with no matching result, appends the fabrication note, and logs the error.
- **The progress block is rendered by the executor.** One row definition controls label order and icons. Deltas use rounded values, keeping the three figures on each line consistent.
- **The blocks own the numbers.** The prompt asks for one short sentence describing what to prioritise, without restating figures from the block.
- **Suggestions are split by what fits, and rendered like the progress block.** `targets.suggest` sizes one typical serving per food and checks it against the room left on kcal, fat and carbs, returning `fits`, `over` (each pick carrying the breach in grams) and `off_catalog_ok` — set only when fewer than `MIN_FITTING_PICKS` catalog foods fit, which is the reply's licence to name a food the user hasn't saved. `targets.render_suggestions` then turns that into the finished `suggestions_block` (`🥩 skyr — 210g (~19g protein)`; counted foods take the count in front and **no invented noun**, since the catalog never recorded whether an `each` is a can or a fillet), which the prompt reproduces verbatim — the model used to format these bullets itself and invented a fresh heading per reply ("Ideas to close the gaps:") off identical data. Icons and macro words are derived from `PROGRESS_ROWS`, so the two blocks can't drift apart. The fitting/breaching split is never collapsed: a pick that closes protein by going past fat names the breach on its own line under `Doesn't quite fit`, or (past the ceiling, where nothing fits by construction) under a heading that says so once. Off-catalog suggestions stay **out** of the block and carry **no macro numbers**: the model names them from its own knowledge, and eating one goes through the estimate gate like any unknown food.
- **Meal labels are whatever the user calls them, never numbered.** `normalise_meal` lowercases and trims; that's all. Several messages labelled `breakfast` are one breakfast (numbering used to split them into `breakfast-1`/`breakfast-2` with no way to merge back), and a real second sitting is whatever they type. An omitted label stores `UNLABELLED_MEAL` and the bot asks — **it must not infer the meal from the clock**, because the user often logs a whole day retrospectively.
- **Catalog removal records a correction.** The removal pins the saved slug and ingestion timestamp. The writer checks the version inside its transaction before appending. Replay deletes that version and preserves past food logs and later saves.
- **Catalog defaults can override a message's meal.** This separates supplements and snacks from other items in the same message. One call can write multiple meals. Explicit meal corrections during confirmation take precedence on that path. Rebuild replays the stored label.
- **Guessed *amounts* auto-commit; only guessed *macros* are gated.** That's deliberate, not an oversight — corrections are what make it safe, so a wrong guess is a one-message fix rather than a hand-edit. (The old ROADMAP question about gating amounts is resolved this way.)
- **Corrections append events.** Each event pins the targeted ingestion timestamp. Replay applies it only to that version. Amount edits rescale macros, while a date or reference-unit change needs a delete and a new entry. Food edits and deletes return the recomputed day totals.
- **`set_meal` is the one correction that writes a dedupe-key column** (`meal`), because food is logged before its label is known. It is safe only because the event pins the exact rows it resolved by `ingested_at`: a blanket "relabel whatever is unlabelled on this date" would, on rebuild, sweep up later rows that were never unlabelled at the time (corrections replay after every food row). `tests/test_rebuild_roundtrip.py::test_a_relabel_does_not_sweep_up_later_unlabelled_rows` is that proof — don't relax it to a `WHERE meal='unlabelled'` sweep.
- **Where macros come from is a four-step ladder, not a source list** (the WHERE MACROS COME FROM block in `prompts.py`). (1) *Has it calories?* Black coffee, water, zero-sugar drinks and most supplements don't — they log via `log_food` with five explicit zeros, no search and **no estimate gate**, because gating a zero buys nothing and costs a round-trip. (2) *In SAVED FOODS?* Then the stored macros win and are never re-checked against the web. (3) *Is a brand, chain or venue named?* Then the producer's **own site** first — no grocer lists a Pret cappuccino, and only Pret has their recipe; if they publish nothing usable, a typical UK version, said out loud. (4) *Otherwise* it's a raw ingredient: estimate it when confident, else a UK grocer (waitrose.com → tesco.com → marksandspencer.com → sainsburys.co.uk → gov.uk/nutrition.org.uk). The ladder replaced a flat "search sparingly" plus one grocer order on 2026-07-26 — that shape sent branded items to grocers that don't stock them, and its blanket trigger is why an iced americano got estimated from general knowledge instead of looked up. A distinction it turns on: an iced *americano* is zero calories, an iced *cappuccino* isn't.
- **Web-sourced macros are still estimates.** Steps 3 and 4 above both end at `propose_food_estimate` → user's "yes" → `confirm_pending`, with the source named in the reply. No new write path exists for them. Search is biased to the UK via `user_location`, **not** restricted by `allowed_domains`: a hard allowlist fails shut on a food no UK grocer lists, and the retailers most likely to have it block automated fetches anyway (measured 2026-07-25: Waitrose/Tesco/Sainsbury's 403; M&S serves its table). Source priority lives in the prompt so it can degrade.
- **A confirmed estimate offers itself to the catalog.** `confirm_pending` returns `catalog_offer` for any committed food not already saved, and the standing offer rides `_offer` + the `log_system_context` fragment so a later "yes" (or better numbers off a label) resolves to `save_food`. The food is logged either way — the offer is a convenience, not a gate. **The offered macros are restated per the catalog's reference portion, not per what was eaten** (`_offer_item`: 100 for `g`/`ml`, 1 for `each`) — 150 g of mince is offered per 100 g, two slices of pizza per one. Scaling is proportional either way; this is so the catalog listing doesn't fill up with "per 150 g" rows that read as mistakes.
- **Exercise is append-per-entry** (`date, exercise, ingested_at`), like `food_log` and unlike `steps`. Logging bench twice in a day is two pieces of work, not a correction of the first. Every measure but the name is nullable so one tool covers weights, bodyweight and timed work; `duration_min` is **per set**, so review multiplies by `sets` for total time.
- **The message transcript is not a system of record** (`health/store/msg_log.py` → `data/messages/<date>.jsonl`). It records every inbound message, tool call (args + result or error), web lookup and outbound reply, including turns that write nothing — which is the gap it closes, since `raw` only exists on rows that got written and `ingest_log.jsonl` stores a hash, not the text. **Server-tool lines are summaries by design** (`harness._summarise_server_result`): a search keeps up to `MAX_SERVER_RESULTS` titles + URLs, a fetch keeps the URL it read, and both drop the payload — a search hit carries `encrypted_content` and a fetch carries the whole retrieved document, so writing them verbatim would put multi-KB blobs into a file appended on every turn. `rebuild_db` never reads it, nothing projects from it, and it is the one writer that swallows its own errors: an observability side-channel must never turn a logged meal into a user-visible failure. **It also carries kind `usage` — one line per API call** (`harness._record_usage`), with token counts, the cache read/write split, and the model and effort in force. That is the bot's only cost signal: `response.usage` was discarded before this, which made prompt caching unverifiable (a cache hit is *only* visible as `cache_read_input_tokens`) and left "what does this cost?" answerable solely by watching the credit balance run out. It is recorded before any branch in the loop, so a paused or refused turn still reports the call it cost. `health/report_usage.py` is the read side.

## Repairing / editing logged data safely

**First resort: just tell the bot.** "delete that latte", "the chickpeas were 40g" — `recent_entries`/`query_log` + `edit_entry`/`delete_entry` handle it, an amount edit rescales the macros, and the change is itself an append-only event. `/today`, `/yesterday`, `/week` and `/last N` print the same rows as a numbered list you can point at ("delete 2"); `/today` and `/yesterday` add that day's progress block under the list; `/week` and `/last N` don't, since neither covers a single day. The numbering is remembered per chat for `LISTING_EXPIRY` (30 min) and then deliberately forgotten, because acting on a stale number deletes the wrong row silently. Reach for the JSONL surgery below only for something the tools can't express (moving a row's date, fixing a catalog entry, repairing corruption).

Because SQLite is just a projection, fix data at the JSONL layer, then rebuild:

1. **Stop the bot cleanly:** `launchctl bootout gui/$(id -u)/local.health-bot` (KeepAlive only relaunches on a *crash*/unclean exit, so a clean bootout stays stopped). This is required — the bot holds an open SQLite connection, and `rebuild_db` deletes and recreates the DB file.
2. Edit the domain JSONL (`data/<domain>.jsonl`) — and the matching `ingest_log.jsonl` line for consistency. Back up first. If a `corrections.jsonl` event points at the row you're changing, fix or drop it too, or it will match nothing (or the wrong thing) on replay.
3. `.venv/bin/python -m health.rebuild_db`.
4. Restart with `./scripts/bot.sh install` (not `restart` — after a bootout the service is unloaded, and `restart`'s `kickstart -k` needs it loaded).

To *change a catalog entry*, prefer re-running the seed loader for just that item so provenance stays consistent, e.g.
`.venv/bin/python -c "from health.example_catalog import INGREDIENTS; from health.seed_catalog import load; load([i for i in INGREDIENTS if i['name']=='<name>'])"`.

## Config & security

`.env` (loaded by `health/config.py`, gitignored) must define `ANTHROPIC_API_KEY`, `TELEGRAM_BOT_TOKEN`, and `ALLOWED_CHAT_ID`. `.env.example` lists every value and which entrypoint needs it. `MODEL` (default `claude-sonnet-5`) selects the routing model. **Changing it invalidates the prompt cache** (caches are model-scoped) — one cold prefix, self-healing on the next message; editing any tool schema does the same, since tools render at position 0. `MAX_TOKENS` (8192) and `EFFORT` (`medium`) live in `harness.py`, not `.env`. 8192 is because on the Claude 5 family thinking is on by default and shares that cap with the reply; the adapter splits any reply over Telegram's 4096-**char** limit, so the slack goes to reasoning. **Do not "save tokens" by disabling thinking**: on the Claude 5 family a thinking-disabled model can emit a tool call as plain visible text — the call silently never runs, no error — which is disqualifying for a bot that is nothing but tool calls. Lower `EFFORT` instead, and watch calls-per-message in `report_usage` for the regression that causes (fewer tool calls means a skipped web lookup or `get_day_totals`, which reads as a perfectly fine reply). The bot **refuses to start without `ALLOWED_CHAT_ID`** — it's the security boundary: any message from another chat is dropped silently (no reply, so the bot's existence isn't confirmed to strangers). `data/` (JSONL, SQLite, logs) is gitignored — it's the owner's health data.
